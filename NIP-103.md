# Entitlement Grant Draft

`draft` `optional` `unallocated event kind`

A standardized event for a merchant to grant a recipient durable, non-monetary access to a listing — including promotional claims, complimentary copies, review keys, contest prizes, and migrated licenses.

It complements [NIP-102](NIP-102.md): NIP-102 proves a payment-backed acquisition; this draft proves an entitlement issued without payment. Neither credential subsumes the other.

This document is deliberately marketplace-agnostic. Verification-relevant facts live in tags; optional human-readable details live in encrypted `.content`. Campaign rules, fulfillment delegation, HTTP issuance flows, and revocation policy belong to the consuming protocol.

This draft intentionally allocates only the buyer-specific entitlement credential. A consuming protocol MAY define a separate policy or campaign event kind when policy has a different signer, lifecycle, or discovery model. That additional kind is a deliberate protocol-layer tradeoff and is not part of this generic grant format.

## Event-kind allocation

The event kind for Entitlement Grants is not allocated by this draft.

Examples use `<entitlement-grant-kind>` as a symbolic placeholder. Implementations MUST NOT substitute an existing assigned kind or deploy an experimental value as an interoperable production standard. The previously proposed `kind:1021` MUST NOT be used because it is already assigned by NIP-15.

## Entitlement Grant Event

An Entitlement Grant is a regular, non-replaceable event. Its permanence is intentional: the initial grant and every later status update form an append-only record and MUST NOT be silently replaced.

The initial event MUST be signed by:

- the merchant's own keypair; or
- a keypair that the consuming protocol independently defines as authorized to issue grants on the merchant's behalf.

This draft does not define delegation.

### Tags

| Tag | Value | Description |
|---|---|---|
| `d` | `<grant-id>` | Stable public grant identifier. Required and relay-indexable under NIP-01. SHOULD be a UUID v4. |
| `p` | `<recipient-pubkey>` | Recipient public key. Required and indexed. |
| `a` | `<addressable-resource-coordinate>` | Addressable Nostr resource to which the entitlement applies. Required. |
| `source_event` | `<event-id>` | Optional immutable policy/source event whose terms authorized issuance. A consuming protocol MAY require it. |
| `authorization` | `<authorization-root-event-id>` | Optional immutable delegated-issuer authorization anchor. A consuming protocol MUST require it when delegated issuance is used and MUST define its verification. |
| `reason` | Free text | Optional informational reason, such as `promotional-claim`, `review-copy`, `migration`, or `contest-prize`. Verifiers MUST NOT assign it security meaning unless a consuming protocol explicitly does so. |
| `status` | `granted` \| `revoked` | Current grant state. Required. The root event MUST use `granted`. |
| `e` | `<preceding-grant-event-id>` | Required exactly once on each status update; absent on the root event. References the immediately preceding event in the same grant chain. |

`d` is used for the grant identifier because NIP-01 relay filters only standardize indexed queries for single-letter tag names. This allows portable `#d` grant-chain lookup without assuming relay-specific indexing of a multi-character `grant` tag.

`source_event` is deliberately distinct from `e`:

- `e` is used only for the grant status chain;
- `source_event` identifies external policy or source terms;
- `authorization` identifies the delegated signer authority. The fields MUST NOT be overloaded or treated as interchangeable.

### Content

`.content` MAY be empty. If present, it MUST be NIP-44-encrypted JSON to the recipient. No field in `.content` is load-bearing for verification.

Suggested plaintext:

```jsonc
{
  "grant_id": "<same as d tag>",
  "reason": "promotional-claim",
  "notes": "Claimed during launch week.",
  "granted_at": 1700000000
}
```

### Root example

```jsonc
{
  "kind": "<entitlement-grant-kind>",
  "pubkey": "<issuer-pubkey>",
  "created_at": 1700000000,
  "tags": [
    ["d", "9c2f1e4a-3b7d-4f21-9a6e-2d8c1f0a5b3e"],
    ["p", "<recipient-pubkey>"],
    ["a", "30402:<merchant-pubkey>:my-product-uuid"],
    ["source_event", "<immutable-policy-event-id>"],
    ["authorization", "<delegated-authorization-root-id>"],
    ["reason", "promotional-claim"],
    ["status", "granted"]
  ],
  "content": "",
  "id": "<event-id>",
  "sig": "<issuer-signature>"
}
```

## Lifecycle and chain invariants

The root event MUST:

- contain exactly one `d`, `p`, `a`, and `status` tag;
- use `status: granted`;
- contain no predecessor `e` tag.

A status update MUST:

- use the same event kind as the root;
- contain exactly one predecessor `e` tag;
- reference the immediately preceding event in the same chain;
- preserve the root's `d`, `p`, `a`, `source_event`, and `authorization` values exactly;
- contain exactly one `status` tag.

A verifier MUST reject a chain when:

- an invariant field changes;
- an update has zero or multiple predecessor tags;
- a predecessor belongs to another grant identifier;
- a cycle or self-reference exists;
- more than one unreferenced chain tip exists;
- any event signature is invalid;
- any event was signed by a key unauthorized for that transition under the consuming protocol.

Verifiers MUST NOT resolve forks by choosing the event with the greatest `created_at`.

Clients SHOULD query all events for a grant using:

```jsonc
["REQ", "grant-sub", {
  "kinds": ["<entitlement-grant-kind>"],
  "#d": ["9c2f1e4a-3b7d-4f21-9a6e-2d8c1f0a5b3e"]
}]
```

The authoritative status is the unique valid chain tip.

## Entitlement detection

Because `p` tags are indexed, clients may discover grants addressed to a recipient using:

```jsonc
["REQ", "recipient-grants", {
  "kinds": ["<entitlement-grant-kind>"],
  "#p": ["<recipient-pubkey>"]
}]
```

## Proof of Entitlement

A resolved grant chain constitutes Proof of Entitlement when:

1. Every event has a valid signature.
2. The root signer is the merchant or an issuer independently authorized by the consuming protocol.
3. Every status transition signer is authorized by the consuming protocol for that transition.
4. The chain satisfies all lifecycle invariants.
5. The `p` tag matches the recipient.
6. The `a` tag matches the claimed resource.
7. The unique chain tip has `status: granted`.
8. Any consuming-protocol requirements for `source_event` and `authorization` are satisfied.

This draft defines no payment, price, campaign, delegation, or issuance-endpoint checks.

## Revocation semantics

A grant has no automatic expiration. It remains valid independently of current listing price or current acquisition policy until a valid `status: revoked` transition is published.

This draft does not determine who may revoke a grant or under what commercial circumstances revocation is legitimate. The consuming protocol MUST define the signer authority for revocation. Cryptographic validity of a revocation does not by itself establish contractual legitimacy.

## Delegation

This draft intentionally defines no delegation, key rotation, authorization interval, or campaign authority model. Consuming protocols may authorize delegated issuance while reserving policy changes and revocation to the merchant's identity key.

## Privacy considerations

- Relay operators can observe public tags including recipient, resource, and status.
- Optional `.content` MUST use NIP-44 when present.
- Grants MAY be transported using NIP-59 Gift Wrap for stronger privacy, at the cost of public `#p` discoverability.
- Recipients and issuers SHOULD retain local copies of grant chains and required source events.

## Implementation notes

- The event kind remains unallocated.
- Issuers MUST NOT publish more than one root event for the same `d` grant identifier.
- Duplicate grants with different `d` identifiers may exist and remain independently valid.
- This draft defines event shape and baseline verification only.

## Reference implementation checklist

- [ ] Use a formally allocated regular-event kind.
- [ ] Create a root event with unique indexed `d`, indexed `p`, resource `a`, and `status: granted`.
- [ ] Preserve chain invariants across every update.
- [ ] Reject cycles, self-references, forks, and changed invariant fields.
- [ ] Verify root issuance authority and transition-specific authority.
- [ ] Resolve only a unique valid chain tip.
- [ ] Treat `reason` as informational.
- [ ] Validate consuming-protocol requirements for distinct `source_event` and delegated `authorization` anchors.
