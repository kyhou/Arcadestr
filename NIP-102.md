# NIP‑102: Marketplace Receipt

`draft` `optional`

A standardized event for cryptographically verifiable marketplace receipts on Nostr. It bridges product listings ([NIP‑99](99.md)), payment proofs, and digital goods fulfillment ([NIP‑98](98.md)) into a complete, auditable commercial pipeline that does not rely on any central authority.

## The `kind:1020` Receipt Event

A Marketplace Receipt is a **regular** (non‑replaceable) event of `kind:1020`. Its permanence is intentional: receipts are legal and financial records and MUST NOT be silently replaced or deleted by the issuing party.

The event MUST be signed by the **merchant's keypair**.

### Tags

| Tag | Value | Description |
|-----|-------|-------------|
| `order` | `<order‑id>` | A unique, public order identifier (merchant‑generated UUID). Required for status tracking and fulfillment. |
| `p` | `<customer‑pubkey>` | The buyer's public key. MUST be present and indexed. |
| `e` | `<zap‑receipt‑event‑id>` | Reference to a `kind:9735` Zap Receipt that proves payment. **Optional** if `bolt11` and `preimage` are present. |
| `a` | `<30402‑coordinate>` | Reference to the classified listing (`kind:30402`) that was purchased. MUST be present. |
| `bolt11` | BOLT‑11 string | The Lightning invoice that was settled. Provides self‑contained payment verification. |
| `preimage` | `<payment‑preimage>` | 32‑byte hex‑encoded payment preimage for the `bolt11` invoice. MUST be present if `bolt11` is provided. |
| `r` | `<external‑receipt‑url>` | Optional HTTPS URL to a human‑readable receipt, authenticated via [NIP‑98](98.md). |
| `status` | `paid` \| `refunded` \| `disputed` | Current settlement status of the order. Defaults to `paid`. |
| `currency` | ISO 4217 or ticker (e.g. `USD`, `EUR`, `BTC`) | Currency in which the transaction is denominated. |
| `amount` | Numeric string | Total amount paid in the specified currency. |
| `invoice` | BOLT‑11 string | (Deprecated alias for `bolt11`; use `bolt11` instead.) |

### Content

The `.content` field MUST contain a [NIP‑44](44.md)-encrypted JSON object, readable only by the merchant and the customer (encrypted to the customer's pubkey). This preserves itemized transaction details from relay operators and the public while keeping the data verifiable by the two transacting parties.

The plaintext JSON object inside `.content` MUST follow this structure:

```jsonc
{
  "order_id": "<same as the 'order' tag>",
  "items": [
    {
      "product_id": "<d‑tag of the kind:30402 listing>",
      "name": "Example Product",
      "sku": "SKU‑001",
      "quantity": 1,
      "unit_price": "49.99",
      "currency": "USD"
    }
  ],
  "subtotal": "49.99",
  "tax": "4.50",
  "shipping": "0.00",
  "total": "54.49",
  "currency": "USD",
  "shipping_address": "<optional — omit for digital goods>",
  "notes": "Digital delivery. License key sent to buyer pubkey.",
  "fulfilled_at": 1700000000
}
```

`shipping_address` and `shipping` MAY be omitted for digital goods.

### Example Event

```jsonc
{
  "kind": 1020,
  "pubkey": "<merchant‑pubkey>",
  "created_at": 1700000000,
  "tags": [
    ["order", "order_3f7a2b9c"],
    ["p", "<customer‑pubkey>"],
    ["a", "30402:<merchant‑pubkey>:my‑product‑uuid", "wss://relay.example.com"],
    ["bolt11", "lnbc..."],
    ["preimage", "a1b2c3d4..."],
    ["r", "https://merchant.example.com/receipts/order_3f7a2b9c"],
    ["status", "paid"],
    ["currency", "USD"],
    ["amount", "54.49"]
  ],
  "content": "<NIP‑44 encrypted JSON>",
  "id": "<event‑id>",
  "sig": "<merchant‑signature>"
}
```

## Payment Proof Flexibility

A receipt MUST include at least one form of payment proof. Implementors SHOULD support both options:

1. **Zap Receipt (`e` tag):** a valid `kind:9735` event from the same merchant, referencing the settled Lightning invoice. Requires relay access to verify.
2. **Self‑contained (`bolt11` + `preimage` tags):** the exact BOLT‑11 invoice string and the payment preimage. Any verifier can compute `sha256(preimage)` and compare with the invoice's payment hash **without** needing an external event.

Merchants MAY include both for maximum compatibility, but at least one pair must be valid.

## Order Status Lifecycle

The initial receipt event (`status: paid`) MUST be unique for a given `order` tag value. Status changes (refund, dispute, fulfillment) are published as **additional** `kind:1020` events with the same `order` tag, an `e` tag referencing the immediately preceding receipt event, and the new `status`. This creates an append‑only, tamper‑evident audit trail.

Clients SHOULD subscribe to all events for a given order using:

```jsonc
["REQ", "order‑sub", {
  "kinds": [1020],
  "#order": ["order_3f7a2b9c"]
}]
```

and consider the **latest** event (by `created_at` or chain traversal) as the authoritative status.

## Purchase Detection

Because `p` tags are indexed by relays, any client can subscribe to receipts addressed to a specific buyer without polling every merchant's relay:

```jsonc
["REQ", "<sub‑id>", {
  "kinds": [1020],
  "#p": ["<customer‑pubkey>"]
}]
```

Clients SHOULD decrypt the `.content` field locally after retrieval and MUST NOT forward the plaintext to any third party without explicit user consent.

## Proof of Ownership

A receipt event constitutes a **Proof of Ownership (PoO)** when:

1. The event is signed by a pubkey the buyer trusts as the merchant (verified e.g. via [NIP‑05](05.md)).
2. The `p` tag matches the buyer's pubkey.
3. The `a` tag matches the product listing the buyer claims to have purchased.
4. At least one payment proof is valid:
   - **If `e` tag present**: the referenced `kind:9735` Zap Receipt is valid per [NIP‑57](57.md) (correct signature, settled status, preimage matches invoice payment hash).
   - **If `bolt11` + `preimage` present**: `sha256(hex_decode(preimage))` equals the payment hash extracted from the `bolt11` invoice, and the invoice is settled (payment time ≤ current time with reasonable tolerance).

The proof is relay‑independent and can be validated offline if the self‑contained payment proof is used.

## Integration with NIP‑98 for Digital Goods Fulfillment

For digital products (software, media, API tokens), purchase detection MUST trigger automated fulfillment. The flow is:

1. **Buyer** authenticates to the merchant's fulfillment server by presenting a signed `kind:27235` event ([NIP‑98](98.md)) that includes the order ID as a parameter (e.g. `?order=order_3f7a2b9c`).
2. **Fulfillment server** queries relays for a `kind:1020` event with `#order` matching that order ID and `#p` matching the buyer's pubkey.
3. The server MUST verify that the latest receipt's `status` is `paid` and that the payment proof is valid (as in Proof of Ownership). It MUST NOT rely solely on the receipt's existence or its tags.
4. If validation passes, the server delivers the digital good or issues a license token.
5. The server SHOULD publish a fulfillment status update: a new `kind:1020` event with the same `order` tag, an `e` tag pointing to the paid receipt, and the tag `["status", "fulfilled"]`.

## Verified Buyer Reviews

A review event (`kind:1985`) MAY include a pointer to a `kind:1020` receipt to assert that the reviewer is a verified buyer:

```jsonc
{
  "kind": 1985,
  "tags": [
    ["L", "com.nostr.marketplace.review"],
    ["l", "verified‑purchase", "com.nostr.marketplace.review"],
    ["e", "<kind:1020‑receipt‑event‑id>"],
    ["a", "30402:<merchant‑pubkey>:product‑uuid"]
  ],
  "content": "Excellent product, fast delivery.",
  ...
}
```

Clients rendering reviews SHOULD:

1. Resolve the referenced `kind:1020` event.
2. Confirm its `pubkey` (merchant) matches the reviewed listing's author.
3. Confirm the `a` tag in the receipt matches the listing being reviewed.
4. Confirm the `p` tag matches the review author's pubkey.
5. Confirm the payment proof is valid as per Proof of Ownership.

Reviews that pass all five checks SHOULD be displayed with a **Verified Purchase** indicator.

## Privacy Considerations

- The `.content` field MUST be encrypted with [NIP‑44](44.md). The deprecated [NIP‑04](04.md) MUST NOT be used.
- Relay operators will see the existence of a receipt and its public tags (`p`, `order`, `status`, `amount`, etc.) but cannot read itemized order details.
- The `p` tag exposes the buyer’s pubkey, which is a deliberate trade‑off to enable relay indexing. For strongly private transactions, receipts MAY be wrapped in [NIP‑59](59.md) Gift Wrap and delivered directly to the buyer, but then they cannot be discovered via `#p` queries.
- Merchants SHOULD transmit `kind:1020` events over relays that enforce authenticated writes ([NIP‑42](42.md)) to prevent spoofed receipts.
- Buyers SHOULD verify the merchant's pubkey against a trusted [NIP‑05](05.md) identifier before accepting a receipt as authoritative.

## Implementation Notes

- **Kind number:** `1020` is a regular (non‑replaceable, non‑ephemeral) event kind. Relays MUST store these events permanently.
- **Relay storage:** Relays SHOULD store `kind:1020` events for as long as feasible. Merchants and buyers SHOULD retain their own copies to guarantee auditability.
- **Merchant key hygiene:** Merchants SHOULD use a dedicated keypair for signing receipts, separate from their social identity key, to limit exposure in the event of key compromise.
- **Idempotency:** Merchants MUST NOT publish more than one initial `kind:1020` event for the same `order` tag value. Status updates are new events that reference the previous one via an `e` tag.
- **Order ID format:** The `order` tag value SHOULD be a version 4 UUID, but any string that uniquely identifies the order within the merchant’s domain is acceptable.

## Reference Implementation Checklist

For a client or merchant backend to be considered NIP‑102 compliant it SHOULD implement:

- [ ] Signing and publishing `kind:1020` upon settlement of a payment, including a unique `order` tag.
- [ ] Encrypting order details in `.content` with NIP‑44 to the customer's pubkey.
- [ ] Subscribing to `{"kinds":[1020],"#p":["<own‑pubkey>"]}` to display purchase history.
- [ ] Supporting both Zap Receipt and self‑contained `bolt11`+`preimage` payment proofs.
- [ ] Verifying the Proof of Ownership chain before displaying a receipt as valid.
- [ ] Handling status updates by subscribing to `#order` and showing the latest state.
- [ ] Including the order ID in NIP‑98 fulfillment requests and checking receipt status before delivery.
- [ ] Displaying a **Verified Purchase** indicator on reviews that include a valid receipt pointer.
